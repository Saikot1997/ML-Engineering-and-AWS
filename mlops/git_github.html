Version Control System (VCS) কী এবং কেন দরকার?

কল্পনা করো তুমি একটা বড় প্রজেক্টের কোড লিখছ। একদিন কোনো পরিবর্তন করার পর সব কিছু নষ্ট হয়ে গেল। যদি আগের version সংরক্ষণ থাকত, তাহলে ফিরে যাওয়া যেত। এই কাজটাই করে Version Control System (VCS)।

মনে করো তুমি Microsoft Word-এ একটি thesis লিখছ। তুমি বিভিন্ন সময়ে thesis_v1.docx, thesis_v2.docx, thesis_final.docx, thesis_FINAL_REAL.docx — এভাবে copy করে রাখছ। এটা হলো manual version control। VCS এই কাজটা স্বয়ংক্রিয়ভাবে এবং অনেক বেশি বুদ্ধিমানের সাথে করে।

VCS কেন দরকার?

🕒 ইতিহাস সংরক্ষণ
কে, কখন, কী পরিবর্তন করেছে — সব জানা যায়। ভুল হলে আগের অবস্থায় ফিরে যাওয়া যায়।
👥 দলগত কাজ
একাধিক ডেভেলপার একই প্রজেক্টে একসাথে কাজ করতে পারে — কেউ কারো কাজ নষ্ট না করে।
🌿 Branch
Main code নষ্ট না করে নতুন feature তৈরি করা যায় আলাদা শাখায়।
🔍 পর্যালোচনা
কোনো পরিবর্তন deploy করার আগে review করা যায়।

Git বনাম পুরনো VCS (SVN, CVS) — Centralized vs Distributed

Centralized (SVN) বনাম Distributed (Git) — পার্থক্য

Git হলো একটি Distributed VCS। মানে প্রতিটা ডেভেলপারের কম্পিউটারে সম্পূর্ণ code history থাকে। নেটওয়ার্ক ছাড়াও কাজ করা যায়।

Git তৈরি করেছিলেন Linus Torvalds ২০০৫ সালে — যিনি Linux kernel-ও তৈরি করেছিলেন।

Terminal

# Homebrew দিয়ে ইন্সটল করো brew install git

🪟 Windows

Git-এর official website (git-scm.com) থেকে installer নামিয়ে install করো। সাথে Git Bash পাবে — এটা Linux-এর মতো terminal।

ইন্সটলেশন যাচাই

Terminal
git --version git version 2.43.0

প্রথমবার সেটআপ — নাম ও ইমেইল

Git প্রতিটি commit-এ তোমার পরিচয় রাখে — কে কোন পরিবর্তন করেছে। তাই প্রথমে নিজের নাম ও ইমেইল দিয়ে রাখো।

Terminal — একবারই করতে হবে
# তোমার নাম সেট করো git config --global user.name "তোমার নাম" # তোমার ইমেইল সেট করো git config --global user.email "তোমার@ইমেইল.com" # সব config দেখো git config --list
--global মানে এই সেটিংস তোমার পুরো কম্পিউটারের সব Git project-এ লাগু হবে। নির্দিষ্ট একটা project-এর জন্য আলাদা করতে চাইলে --global বাদ দিয়ে শুধু সেই folder থেকে কমান্ড দাও।

নতুন Repository তৈরি করা

Terminal
# প্রথমে একটা folder তৈরি করো mkdir আমার-প্রজেক্ট cd আমার-প্রজেক্ট # সেই folder-কে Git repository হিসেবে শুরু করো git init Initialized empty Git repository in /আমার-প্রজেক্ট/.git/
mkdir কী? "Make Directory" — নতুন folder তৈরির কমান্ড।
cd কী? "Change Directory" — সেই folder-এ ঢোকার কমান্ড।
git init কী করে? folder-এর ভেতরে একটা লুকানো .git folder তৈরি করে — এখানেই সব history থাকে। এই folder মুছলে সব history নষ্ট।

.gitignore — কোন file ignore করবে?

অনেক file Git-এ রাখা উচিত না — যেমন password ফাইল, build output, temporary ফাইল। .gitignore ফাইলে এদের নাম লিখলে Git এগুলো দেখে না।

.gitignore ফাইলের উদাহরণ
# .gitignore ফাইলে এগুলো লিখো: *.pyc # সব .pyc ফাইল ignore করো __pycache__/ # এই folder ignore করো .env # এই ফাইলে password থাকে — কখনো push করো না! node_modules/ # JavaScript project-এর বড় folder *.log # সব log ফাইল
.env ফাইলে password/API key থাকে। এটা কখনো GitHub-এ push করো না! সবসময় .gitignore-এ রাখো।

Git-এর মূল ধারণা — তিনটি এলাকা

Git-কে বোঝার জন্য সবচেয়ে গুরুত্বপূর্ণ হলো এর তিনটা "এলাকা" বোঝা। প্রতিটা file এই তিন জায়গার যেকোনো একটায় থাকে।

Git-এর তিন স্তর: Working Directory → Staging Area → Repository

🟠 ১. Working Directory (কাজের এলাকা)

তোমার সাধারণ folder। তুমি এখানে file তৈরি করো, edit করো। Git এই পরিবর্তনগুলো দেখে কিন্তু এখনো track করে না।

🟡 ২. Staging Area / Index

git add দিয়ে যে files যোগ করো সেগুলো এখানে আসে। মানে বলছ — "এই পরিবর্তনগুলো আমি পরের commit-এ রাখতে চাই।"

ভাবো তুমি একটা চিঠি লিখছ। Working Directory হলো তোমার ড্রাফট খাতা। Staging Area হলো খামের ভেতরে রাখার আগের অবস্থা। Commit হলো খাম সিল করে পাঠিয়ে দেওয়া।

🔵 ৩. Git Repository (.git folder)

Commit করলে পরিবর্তনগুলো চিরতরে সংরক্ষিত হয়। প্রতিটা commit-এর একটা unique ID (hash) থাকে যেমন a1b2c3d।

File-এর জীবনচক্র

একটি File কীভাবে এক অবস্থা থেকে অন্য অবস্থায় যায়
Untracked মানে Git এই ফাইলের সম্পর্কে কিছুই জানে না — নতুন তৈরি ফাইল।
Modified মানে Git জানে এই ফাইল ছিল, কিন্তু তুমি এটা পরিবর্তন করেছ।
Staged মানে git add করা হয়েছে — পরবর্তী commit-এর জন্য প্রস্তুত।
Committed মানে পরিবর্তন চিরতরে ইতিহাসে সংরক্ষিত।
৪

প্রতিদিনের মূল কমান্ড

git status — সবচেয়ে জরুরি কমান্ড

git status তোমাকে বলে এই মুহূর্তে repository-র কী অবস্থা। প্রতিটা কমান্ডের আগে ও পরে এটা চালানো উচিত।

Terminal
git status # সব ঠিক থাকলে: On branch master nothing to commit, working tree clean # নতুন file আছে কিন্তু add করা হয়নি: Untracked files: doc.txt # file add করা হয়েছে, commit বাকি: Changes to be committed: new file: doc.txt

প্রথম commit — সম্পূর্ণ উদাহরণ

১
File তৈরি করো:
touch doc.txt echo 'আমার প্রথম Git ফাইল' >> doc.txt cat doc.txt আমার প্রথম Git ফাইল
touch কী? একটা খালি ফাইল তৈরি করে।
>> কী? "append" — ফাইলের শেষে লেখা যোগ করে। একটা > হলে পুরো ফাইল মুছে নতুন লেখা বসায়।
cat কী? ফাইলের ভেতরের সব লেখা terminal-এ দেখায়।
২
Status দেখো:
git status Untracked files: doc.txt # মানে: Git এই ফাইল দেখছে কিন্তু track করছে না
৩
Staging-এ যোগ করো:
git add doc.txt git status Changes to be committed: new file: doc.txt # মানে: ফাইলটা staged — commit করার জন্য প্রস্তুত
৪
Commit করো:
git commit -m "doc.txt ফাইল যোগ করা হলো" [master (root-commit) a1b2c3d] doc.txt ফাইল যোগ করা হলো 1 file changed, 1 insertion(+) # -m মানে "message" — commit-এর সাথে বার্তা দাও # a1b2c3d হলো এই commit-এর unique ID (hash)

git log — ইতিহাস দেখা

Terminal
# বিস্তারিত দেখো git log commit a1b2c3d4e5f6 (HEAD -> master) Author: তোমার নাম <তোমার@ইমেইল.com> Date: Mon Apr 13 10:30:00 2026 doc.txt ফাইল যোগ করা হলো # সংক্ষেপে — এক লাইনে প্রতিটা commit git log --oneline a1b2c3d doc.txt ফাইল যোগ করা হলো # গ্রাফ আকারে — branch-এর structure দেখো git log --oneline --graph # কোন file-এ কী পরিবর্তন হয়েছে সেটাও দেখাও git log --oneline --graph --name-status
HEAD কী? HEAD হলো একটা pointer — এই মুহূর্তে তুমি কোন commit-এ আছ সেটা বোঝায়। সাধারণত সর্বশেষ commit-এ থাকে। HEAD~1 মানে HEAD-এর ঠিক আগের commit।

git diff — পার্থক্য দেখা

# দুটো commit-এর মধ্যে পার্থক্য দেখো git diff a1b2c3d e4f5g6h - পুরনো লাইন (লাল — মুছে গেছে) + নতুন লাইন (সবুজ — যোগ হয়েছে) # এখনো unstaged পরিবর্তন দেখো git diff

পিছনে ফেরা — git revert ও git reset

✅ git revert (নিরাপদ)

পুরনো commit-কে "উল্টো" করে নতুন commit তৈরি করে। ইতিহাস মুছে না।

git revert a1b2c3d # একটা নতুন commit হবে যা # a1b2c3d-এর কাজ উল্টে দেবে

দলগত কাজে সবসময় এটা ব্যবহার করো।

⚠️ git reset (বিপজ্জনক)

commit ইতিহাস থেকে মুছে ফেলে।

# শুধু commit বাতিল, code রাখো git reset --soft HEAD~1 # commit + code দুটোই মুছো git reset --hard HEAD~1
--hard flag দিলে code হারিয়ে যাবে — recover করা প্রায় অসম্ভব। দলে কখনো করো না।

git tag — সংস্করণ চিহ্নিত করা

git tag v1.0.0 # বর্তমান commit-কে tag করো git tag # সব tag দেখো

Branch — সমান্তরালে কাজ

Branch হলো Git-এর সবচেয়ে শক্তিশালী feature। তোমার একটা working website আছে (master branch)। নতুন "dark mode" যোগ করতে চাও — সরাসরি master-এ করলে সাইট নষ্ট হতে পারে। তাই আলাদা branch-এ কাজ করো।

Branch ডায়াগ্রাম — সমান্তরাল কাজের ভিজ্যুয়াল

Branch কমান্ড

Branch কমান্ডসমূহ
# সব branch দেখো (* = এখন যেটায় আছ) git branch * master feature/dark-mode # নতুন branch তৈরি করো git branch feature/dark-mode # branch-এ যাও (পুরনো পদ্ধতি) git checkout feature/dark-mode # branch-এ যাও (আধুনিক পদ্ধতি — Git 2.23+) git switch feature/dark-mode # শর্টকাট: তৈরি করো ও সাথে সাথে চলে যাও git switch -c feature/login-page # অথবা পুরনোভাবে: git checkout -b feature/login-page # master-এ এসে feature merge করো git switch master git merge feature/dark-mode # Branch মুছে ফেলো (merge-এর পর) git branch -d feature/dark-mode
git switch কী? এটা git checkout-এর নতুন, পরিষ্কার version। Git 2.23 থেকে চালু হয়েছে। শুধু branch পরিবর্তনের জন্য — আগের checkout একসাথে অনেক কাজ করত যা confusing ছিল।
Branch তৈরির naming convention: feature/কী-করছ, bugfix/কী-ঠিক-করছ, hotfix/জরুরি-fix — এটা পেশাদার পদ্ধতি।
৬

Merge Conflict — দ্বন্দ্ব মেটানো

যখন দুজন ডেভেলপার একই file-এর একই লাইন আলাদা আলাদাভাবে edit করে এবং merge করার চেষ্টা করে, তখন conflict হয়। Git বুঝতে পারে না কোনটা রাখবে — তাই তোমাকে সিদ্ধান্ত নিতে হয়।

Conflict দেখতে কেমন?

merge.txt — conflict হওয়ার পরে ফাইলের ভেতরে
<<<<<<< HEAD আমি master branch-এ যা লিখেছিলাম ======= আমি feature branch-এ যা লিখেছিলাম >>>>>>> feature/dark-mode
<<<<<<< HEAD থেকে ======= পর্যন্ত: তোমার বর্তমান branch (HEAD)-এর লেখা।
======= থেকে >>>>>>> feature/dark-mode পর্যন্ত: যে branch merge করতে চাইছ তার লেখা।
তোমাকে manually সিদ্ধান্ত নিতে হবে — কোনটা রাখবে, কোনটা বাদ দেবে, নাকি দুটোই রাখবে।

Conflict সমাধানের ধাপ

১
Conflict হয়েছে জানো: git status দিলে "both modified" দেখাবে।
২
File খুলে manually ঠিক করো: marker লাইনগুলো মুছে সঠিক content রাখো।
ঠিক করার পরে merge.txt দেখতে এমন হবে
master ও feature উভয় branch-এর লেখা রাখা হলো আমি master branch-এ যা লিখেছিলাম
৩
Resolved করো:
git add merge.txt git commit -m "conflict সমাধান করা হলো"
Conflict এড়াতে: প্রতিদিন git pull করো। ছোট ছোট commit করো। একই file-এ একসাথে কাজ না করার চেষ্টা করো।

GitHub — দলগত কাজের প্ল্যাটফর্ম

Git হলো টুল, GitHub হলো সেই টুল ব্যবহার করে অনলাইনে code সংরক্ষণ ও দলে কাজ করার প্ল্যাটফর্ম।

Git হলো তোমার নিজের diary লেখার পদ্ধতি। GitHub হলো সেই diary অনলাইনে রাখা — বন্ধুরা দেখতে পারে, edit করতে পারে।

Authentication — HTTPS Token

HTTPS Token দিয়ে clone
git clone https://github.com/UserName/my-repo.git Username: তোমার_username Password: ghp_xxxxxxxx ← Personal Access Token (password না!) # Token তৈরি: GitHub → Settings → Developer settings # → Personal access tokens → Generate new token

Authentication — SSH Key (একবার করলেই চিরকাল)

SSH Key Setup
# ধাপ ১: SSH key তৈরি করো ssh-keygen -t ed25519 -C "তোমার@ইমেইল.com" # Enter চাপো (default location accept করো) # Passphrase চাইলে আবার Enter (blank রাখতে পারো) # ধাপ ২: Public key দেখো ও copy করো cat ~/.ssh/id_ed25519.pub ssh-ed25519 AAAAC3Nza... তোমার@ইমেইল.com # ধাপ ৩: GitHub → Settings → SSH Keys → New SSH Key # এই key paste করো # ধাপ ৪: এখন এভাবে clone করো (password লাগবে না) git clone git@github.com:username/repo.git
SSH মানে Secure Shell। এটা public key ও private key-এর জুটি ব্যবহার করে। তোমার private key তোমার কম্পিউটারে থাকে, public key GitHub জানে। এরা মিলে গেলে — password ছাড়াই প্রমাণ হয় যে তুমিই তুমি।

Remote Repository — Push, Pull, Fetch

Local ↔ Remote — কীভাবে sync হয়
Remote কমান্ড
# GitHub repo copy করো (প্রথমবার) git clone https://github.com/username/repo.git # Local changes remote-এ পাঠাও git push origin main # origin = remote-এর default নাম (GitHub) # main = কোন branch push করছ # Remote থেকে changes নামাও + merge করো git pull origin main # শুধু চেক করো — merge করো না git fetch origin # নতুন branch remote-এ পাঠাও (প্রথমবার) git push -u origin feature/dark-mode # -u মানে --set-upstream — এরপর থেকে শুধু git push লিখলেই হবে
fetch vs pull:
git fetch = "দেখো অনলাইনে কী নতুন এসেছে" (তোমার code পরিবর্তন হয় না)
git pull = "নতুন সব নামাও এবং তোমার code-এ যোগ করো" (= fetch + merge একসাথে)

Pull Request ও Fork

Pull Request (PR) কী?

বাস্তব দলগত কাজে সরাসরি main branch-এ merge করা হয় না। কেউ feature তৈরি করে Pull Request খোলে — মানে বলে "আমার পরিবর্তনগুলো main-এ যোগ করুন।" Reviewer দেখে approve করলে তখন merge হয়।

১
নতুন branch-এ কাজ করো ও push করো
২
GitHub-এ গিয়ে "New Pull Request" বোতাম চাপো
৩
কী পরিবর্তন করেছ তা description-এ লিখো
৪
Reviewer code দেখে মন্তব্য দেয়, প্রয়োজনে পরিবর্তন করো
৫
Approve হলে merge করা হয়, branch মুছে ফেলা হয়

Fork কী?

অন্য কারো repository-র সম্পূর্ণ copy তোমার নিজের GitHub account-এ নেওয়াকে Fork বলে।

ভাবো তুমি একটা বিখ্যাত রেস্তোরাঁর recipe বই পেয়েছ (fork)। নিজের বাড়িতে নিয়ে গেলে (clone) এবং নিজের মতো পরিবর্তন করলে। পরে মনে হলো এই উন্নতি মূল রেস্তোরাঁতেও থাকা উচিত — তখন Pull Request পাঠালে।

Git Flow ও GitHub Flow

কমান্ড জানলেই হয় না — কীভাবে ব্যবহার করতে হবে তারও নিয়ম থাকে। এই নিয়মকে Workflow বলে।

Git Flow (বড় প্রজেক্টের জন্য)

Git Flow — সম্পূর্ণ Branch Structure
main
Production-ready stable code। প্রতিটা commit-এ tag লাগানো হয়।
develop
চলমান development-এর branch। Feature branches এখান থেকে বের হয়।
feature/xxx
নতুন feature-এর জন্য। develop থেকে বের হয়, develop-এ merge হয়।
release/x.x
Release-এর আগে testing।
hotfix
Production-এ জরুরি bug fix। main থেকে বের হয়, main ও develop দুটোতেই merge।

CI/CD — Continuous Integration & Deployment

তুমি code push করলে কেউ কি manually test করবে, deployment করবে? না! CI/CD এটা স্বয়ংক্রিয়ভাবে করে।

CI/CD পাইপলাইন — কোড Push থেকে Production পর্যন্ত

🔄 Continuous Integration (CI)

Code push করলে স্বয়ংক্রিয়ভাবে:

  • Code build হয়
  • Tests run হয়
  • Code quality check হয়

🚀 Continuous Deployment (CD)

Test পাস হলে স্বয়ংক্রিয়ভাবে:

  • Production server-এ deploy হয়
  • বা staging-এ যায় (manual trigger)
১২

GitHub Actions — অটোমেশন

GitHub Actions হলো GitHub-এর built-in CI/CD টুল। তুমি YAML ফাইলে লিখে দাও কী করতে হবে, GitHub নিজেই করে।

মূল ধারণাগুলো

🎯 Event
কখন workflow চলবে? Push করলে, PR খুললে, নির্দিষ্ট সময়ে।
💼 Job
এক একটা কাজের সেট। প্রতিটা Job আলাদা virtual machine-এ চলে।
👣 Step
Job-এর ভেতরের ছোট ছোট কাজ। Shell command বা pre-built action।
⚡ Runner
যে virtual machine-এ Job চলে। Linux, Windows, macOS হতে পারে।

প্রথম Workflow

.github/workflows/first_workflow.yml
name: আমার প্রথম Workflow on: push: # যখনই push করবে branches: - main workflow_dispatch: # GitHub UI থেকে manually চালানো যাবে jobs: say-hello: # Job-এর নাম (যেকোনো নাম দাও) runs-on: ubuntu-latest # Linux VM-এ চলবে steps: - name: Hello বলো run: echo "Hello World! আমার প্রথম Action!" - name: Python version দেখো run: python3 --version - name: ফাইল তৈরি করো run: | touch workflow_ran.txt echo "Workflow চলেছে!" >> workflow_ran.txt ls -l
YAML কী? "YAML Ain't Markup Language" — একটা data format যা মানুষ পড়তে পারে। Python-এর মতো indentation (ফাঁকা জায়গা) দিয়ে structure বোঝায়। ভুল indentation দিলে error হয়!

workflow_dispatch কী? এটা থাকলে GitHub-এর Actions tab থেকে manually button চাপলে workflow চলানো যায়।

Pytest ও Flake8 দিয়ে Code Quality Check

এই workflow-টা real project-এ সবচেয়ে বেশি ব্যবহার হয়। Dummy test file সহ দেখানো হলো:

file_test.py — Dummy test file (নিজেই তৈরি করো)
# file_test.py # pytest এই ফাইলে test_ দিয়ে শুরু হওয়া সব function চালাবে def test_addition(): # 2+4 = 6 কিনা পরীক্ষা করো result = 2 + 4 assert result == 6 def test_subtraction(): result = 10 - 3 assert result == 7 def test_multiply(): result = 5 * 4 assert result == 20 def test_string(): name = "hello" assert name == "hello" assert len(name) == 5 # assert কী? এটা বলে "এটা সত্য হওয়া উচিত"। # যদি মিথ্যা হয় — test fail করে।
.github/workflows/test.yml
name: Test ও Code Quality on: push # যেকোনো push-এ চলবে jobs: qa: name: Code চেক করো runs-on: ubuntu-24.04 steps: # ধাপ ১: আমাদের code VM-এ copy করো - name: Repository checkout uses: actions/checkout@v3 # ধাপ ২: Python সেটআপ করো - name: Python সেটআপ uses: actions/setup-python@master with: python-version: "3.x" # ধাপ ৩: দরকারি package install করো - name: প্যাকেজ ইন্সটল run: | pip install pytest flake8 # ধাপ ৪: tests চালাও - name: Tests চালাও run: pytest # ধাপ ৫: code style চেক করো (PEP8 convention) - name: Flake8 code style uses: py-actions/flake8@v2
uses: actions/checkout@v3 কী করে? GitHub-এর marketplace থেকে একটা ready-made action ব্যবহার করে যা virtual machine-এ তোমার code copy করে। এটা ছাড়া VM তোমার code দেখতে পাবে না।

flake8 কী? Python code style checker। যেমন line too long, unused import — এসব ধরে। PEP8 মানে Python-এর official code style guide।

Environment Variables ও Secrets

Environment Variable
# পুরো workflow-এর জন্য variable env: APP_NAME: "MyApp" jobs: greet: runs-on: ubuntu-latest env: MY_NAME: "Hoimi" # এই job-এর জন্য steps: - name: সালাম দাও run: echo "Hello $MY_NAME from $APP_NAME" # গোপন তথ্যের জন্য Secrets ব্যবহার করো: # GitHub → Settings → Secrets → New Secret # তারপর YAML-এ এভাবে ব্যবহার করো: env: API_KEY: ${{ secrets.MY_API_KEY }}
Password, API key, database credential কখনো সরাসরি YAML ফাইলে লিখবে না। সবসময় GitHub Secrets ব্যবহার করো।
