Kubernetes কী? কেন দরকার?
একদম গোড়া থেকে, কোনো prior knowledge ছাড়াই বোঝা যাবে

🎯 সহজ বাংলায় Kubernetes

ধরো তুমি একটা রেস্তোরাঁ চালাচ্ছ। শুরুতে একজন বাবুর্চি ছিল। কিন্তু যখন হাজার জন খদ্দের আসল, একজন বাবুর্চি যথেষ্ট নয়। তুমি অনেক বাবুর্চি রাখলে — কিন্তু তাদের সবাইকে manage করা ঝামেলা। কে কোথায় আছে? কে অসুস্থ? কে বেশি কাজ পাচ্ছে?

Kubernetes হলো সেই manager যে বলে: "এই বাবুর্চি অসুস্থ? No problem, আরেকজনকে নামাও। বেশি অর্ডার? আরও লোক নিয়ে আসো। কম অর্ডার? কিছু বাড়ি পাঠাও।"

প্রযুক্তির ভাষায় — Kubernetes একটা open-source Container Orchestrator, Google এর তৈরি। এটা automatically containerized applications deploy করে, scale করে, monitor করে এবং manage করে।

🔤 নামের মানে: "Kubernetes" গ্রিক শব্দ — মানে "পাইলট" বা নৌকার হেলমসম্যান। Short form: k8s — কারণ k আর s এর মাঝে ঠিক ৮টা অক্ষর!

🐳 Docker vs Kubernetes — এরা কি প্রতিযোগী?

না! এরা দুই বন্ধু। একসাথে কাজ করে।

Docker — Container Runtime

  • Container তৈরি করে এবং চালায়
  • একটা app-কে "বাক্সে" (container) ভরে
  • Single machine এ ভালো কাজ করে
  • ভূমিকা: বাবুর্চি (রান্না করে)

Kubernetes — Orchestrator

  • Containers পরিচালনা করে
  • বহু machine এ containers manage করে
  • Auto-scaling, self-healing করে
  • ভূমিকা: manager (পরিচালনা করে)

✅ সহজ নিয়ম: Kubernetes orchestrate করে, Docker run করে। Kubernetes যখন নতুন container চালাতে চায়, সে Docker-কে বলে সেটা চালু করতে। Docker হলো engine, Kubernetes হলো driver।

❓ কেন Kubernetes দরকার? — Real Example

🎬 একটা ML API এর গল্প

তুমি একটা sentiment analysis model বানিয়েছ। FastAPI দিয়ে serve করছ। একটা server এ চলছে। শুরুতে সব ঠিকঠাক। কিন্তু:

  • হঠাৎ ১০,০০০ request এলো — একটা instance সামলাতে পারল না, সব request fail
  • রাত ৩টায় server crash করল — কেউ নেই জাগিয়ে restart করতে
  • নতুন version deploy করতে গেলে কিছুক্ষণ সার্ভিস বন্ধ রাখতে হয় (downtime)
  • কোন server এ কতটা load, কোন instance healthy — জানার উপায় নেই

Kubernetes এই সব সমস্যার সমাধান:

  • 🔄 Auto-scaling: load বাড়লে আরও instance, কমলে কম instance
  • 🔧 Self-healing: instance crash করলে Kubernetes নিজেই নতুন চালু করে
  • ⚖️ Load Balancing: requests সব instances এ সমানভাবে ভাগ করে দেয়
  • 🚀 Rolling Update: পুরনো version চালু রেখে নতুন deploy করো — zero downtime

Distributed Architecture — মূল ভিত্তি
Cluster, Node, Master, Worker — এগুলো কী এবং কেন?

🏙️ শহরের উপমায় বোঝো

ধরো একটা বড় শহর। শহরে অনেক বিল্ডিং আছে — প্রতিটা বিল্ডিং একটা Node। পুরো শহরটা হলো Cluster। Mayor office যেখান থেকে সব নির্দেশ আসে সেটা হলো Master Node। কর্মীরা যারা সেই নির্দেশ পালন করে কাজ করে তারা হলো Worker Nodes।

Orchestrator (Mayor) সব worker nodes এর status জানে — কেউ অসুস্থ হলে কাজ অন্য কাউকে দেয়।

🏘️ Cluster = অনেক machine এর সমষ্টি
💻 Node = একটা machine (physical বা virtual)
👑 Master Node = নির্দেশ দেয়, manage করে
👷 Worker Node = নির্দেশ পালন করে, containers চালায়

👑 Control Plane (Master Node) Components

Componentভূমিকাসহজ উপমা
kube-apiserver সব communication এর মূল দরজা। kubectl, worker nodes — সবাই এর মাধ্যমে Control Plane এর সাথে কথা বলে। REST API হিসেবে কাজ করে। অফিসের reception desk — সবাই এখানে এসে কথা বলে
etcd Key-value database যেখানে cluster এর সব তথ্য জমা থাকে। কোন Pod কোথায় চলছে, কতটা resource আছে — সব এখানে। এটাই "single source of truth"। অফিসের ফাইল cabinet — সব রেকর্ড এখানে
kube-scheduler নতুন Pod কোন Worker Node এ চালাবে সেটা ঠিক করে। Resource available আছে কিনা, anti-affinity rule আছে কিনা — এসব দেখে। HR manager — কোন কাজ কোন worker কে দেবে
kube-controller-manager Node, ReplicaSet, Endpoints, Service Accounts monitor করে। কিছু ভাঙলে action নেয়। অনেকগুলো controller এক জায়গায় চালায়। Security guard + supervisor
cloud-controller-manager AWS, GCP, Azure এর মতো cloud provider এর সাথে interact করে। Load balancer, storage provision এই কাজ করে। বিদেশি দূতাবাস — বাইরের দুনিয়ার সাথে যোগাযোগ

👷 Worker Node Components

Componentভূমিকাসহজ উপমা
kubelet Worker node এ চলা agent। Container এর health check করে। Master কে report করে। kube-apiserver থেকে নতুন command পেলে apply করে। Factory floor manager — workers ঠিকমতো কাজ করছে কিনা দেখে
kube-proxy Network traffic manage করে। বিশেষত বাইরে থেকে আসা traffic সঠিক Pod এ forward করে। Traffic police — গাড়ি কোথায় যাবে বলে দেয়
Container Runtime Containers আসলে চালায়। Docker, containerd, runc — এগুলো runtime। Kubernetes নিজে container চালায় না, runtime-কে বলে। গাড়ির engine — actual কাজ এটাই করে

⚠️ গুরুত্বপূর্ণ বিষয়: Kubernetes নিজে কিন্তু সরাসরি containers manage করে না! এটা Docker বা containerd-কে বলে container চালাতে। প্রতিটা Worker Node এ আলাদাভাবে Container Runtime install করতে হয়।

⚡ K3s — হালকা Kubernetes (এই course এ ব্যবহার হবে)

🪶 K3s কী?

K3s হলো Kubernetes এর lightweight version। Normal Kubernetes অনেক resource লাগায়। K3s কম resource এ চলে — laptop বা Raspberry Pi তেও চলে। Production এর জন্যও ready।

# K3s install করো (একটা command এ সব হয়) curl -sfL https://get.k3s.io | sh -s - --write-kubeconfig-mode 644 # Kubernetes version check করো kubectl version --short # Output: # Client Version: v1.25.4+k3s1 # Server Version: v1.25.4+k3s1 # Nodes দেখো k3s kubectl get nodes # K3s এ master আর worker একই machine এ — "all-in-one"

✅ K3s এ একটাই machine এ master এবং worker দুটো role পালন করে। Testing ও learning এর জন্য perfect।

Kubernetes Objects — Pod, ReplicaSet, Deployment
Kubernetes এর মূল building blocks — প্রতিটা কী করে?

📦 Pod — Kubernetes এর সবচেয়ে ছোট unit

Pod কী? Docker Container এর সাথে পার্থক্য?

Docker তে Container হলো সবচেয়ে ছোট unit। Kubernetes এ সেটা হলো Pod।

একটা Pod এ এক বা একাধিক container থাকতে পারে। এই containers একই environment share করে — একই storage, একই IP address, একই network namespace।

Pod এর ভেতরের containers localhost দিয়ে একে অপরের সাথে কথা বলতে পারে। বাইরে কথা বলতে হলে port expose করতে হয়।

Pod এর বিভিন্ন রূপ — single container, multi-container, shared volume

❗ সবচেয়ে গুরুত্বপূর্ণ বিষয়: Pod ephemeral মানে ক্ষণস্থায়ী — RAM এর মতো। Computer বন্ধ হলে RAM মুছে যায়, Pod বন্ধ হলে তার data মুছে যায়।

উদাহরণ: Pod এ database চালাচ্ছ, ১০০০ record ছিল। Pod crash করল → নতুন Pod উঠল → কিন্তু সেই ১০০০ record গেছে! এজন্য database এর জন্য সবসময় Persistent Volume ব্যবহার করতে হয়।

🔄 ReplicaSet ও Deployment — Pod ম্যানেজ করে

📊 ReplicaSet — একই Pod এর অনেক copy

ReplicaSet বলে: "আমি সবসময় ৩টা identical Pod চালু রাখব।" কোনো Pod মরে গেলে? ReplicaSet Controller Manager এর মাধ্যমে detect করে এবং তৎক্ষণাৎ নতুন Pod বানায়।

🚀 Deployment — ReplicaSet এর উপরের layer

Deployment হলো ReplicaSet কে manage করে। Deployment দিয়ে:

  • Pods ও ReplicaSets automatically create করা যায়
  • পুরনো version এ rollback করা যায় (history track করে)
  • নতুন version deploy করা যায় downtime ছাড়াই (Rolling Update)
  • Replica count update করা যায়

✅ Best practice: সরাসরি Pod না বানিয়ে Deployment ব্যবহার করো। Deployment → ReplicaSet → Pods hierarchy মেনে চলো।

Deployment → ReplicaSet (versions) → Pods hierarchy

🏷️ অন্যান্য গুরুত্বপূর্ণ Objects

🗂️ Namespace

  • Cluster এর ভেতর virtual sub-cluster
  • আলাদা team/env এর জন্য
  • Default: default, kube-system, kube-public
  • Resource limits দেওয়া যায়
  • Nested করা যায় না

⚙️ ConfigMap ও Secret

  • ConfigMap: Non-sensitive config (env vars, files)
  • Secret: Password, token — base64 encoded
  • Pods এ environment variable হিসেবে inject
  • File হিসেবেও volume mount করা যায়

⏰ Job ও CronJob

  • Job: নির্দিষ্ট কাজ করে শেষ করে
  • CronJob: নির্দিষ্ট সময় পরপর Job চালায়
  • Batch processing এর জন্য দরকার

📊 StatefulSet

  • Database এর মতো stateful apps
  • Stable, unique network identity দেয়
  • Ordered deployment ও scaling
  • Persistent storage automatically attach

🌐 Service

  • Pods expose করে (network access দেয়)
  • Stable IP দেয় (Pod IP বদলালেও সমস্যা নেই)
  • Types: ClusterIP, NodePort, LoadBalancer

🚪 Ingress ও Ingress Controller

  • URL based routing rules define করে
  • /api → Service A, /app → Service B
  • NGINX, Traefik — popular controllers

সব important command বাংলায় ব্যাখ্যা সহ

📖 kubectl এর syntax structure

kubectl [command] [TYPE] [NAME] [Flag]
Partমানেউদাহরণ
commandকী operation করতে চাও?get, create, apply, delete, describe, scale, exec, logs
TYPEকোন resource এর উপর?pod, deployment, service, namespace, replicaset
NAMEresource এর নাম (case-sensitive!)nginx, my-app, wordpress
Flagextra option-f file.yml, -n namespace, --replicas=5
# ══════ GET — দেখো ══════ kubectl get pods # সব pod দেখো (default namespace) kubectl get pods -n kube-system # নির্দিষ্ট namespace এ kubectl get pods -A # সব namespace এর pods kubectl get all # সব resources (pod, svc, deploy...) kubectl get pod --show-labels # labels সহ দেখো kubectl get deployment # deployments দেখো kubectl get svc # services দেখো kubectl get nodes # cluster এর nodes দেখো kubectl get namespace # namespaces দেখো kubectl api-resources # সব resource types দেখো (shortnames সহ) # ══════ CREATE / RUN — তৈরি করো ══════ kubectl run nginx --image=nginx # imperative: সরাসরি Pod তৈরি kubectl create deployment app \ --image=nginx --replicas=3 # deployment তৈরি kubectl apply -f file.yml # declarative: YAML file থেকে kubectl create namespace myns # namespace তৈরি # ══════ DESCRIBE — বিস্তারিত দেখো ══════ kubectl describe pod nginx kubectl describe deployment myapp # events, conditions সব দেখা যায় # ══════ DELETE — মুছে দাও ══════ kubectl delete pod nginx kubectl delete pod nginx wordpress # একসাথে অনেক kubectl delete -f file.yml # ══════ SCALE — সংখ্যা বাড়াও/কমাও ══════ kubectl scale deploy nginx-deployment --replicas=5 # ══════ EXEC — Pod এর ভেতরে ঢোকো ══════ kubectl exec -it mypod -- /bin/bash # shell খোলো kubectl exec mypod -- ls /app # single command চালাও # ══════ LOGS — logs দেখো ══════ kubectl logs mypod kubectl logs mypod -f # live/follow mode kubectl logs mypod --previous # আগের crashed container এর logs # ══════ ROLLOUT — deployment history ══════ kubectl rollout history deployment myapp kubectl rollout undo deployment myapp # আগের version এ ফিরে যাও kubectl rollout restart deployment myapp # সব Pods restart করো

YAML Configuration Files
প্রতিটা field এর মানে বাংলায় — কোনো কিছুই বাদ নেই

📌 YAML কী? YAML = "Yet Another Markup Language" — মানুষের পড়ার মতো configuration language। JSON এর মতোই কিন্তু আরও সহজ।

⚠️ Indentation অত্যন্ত গুরুত্বপূর্ণ! YAML এ space দিয়ে hierarchy বোঝানো হয়। Tab দিলে error হয় — শুধু space ব্যবহার করো। যেমন:

# ✅ সঠিক — 2 space indent spec: containers: - name: nginx # 2 space image: nginx # 4 space (nested) # ❌ ভুল — Tab দিলে এই error আসবে: # yaml: line 3: found character that cannot start any token # ❌ ভুল — inconsistent indent spec: containers: # 3 space — কিন্তু আগের জায়গায় 2 space ছিল - name: nginx # এটা error দেবে

🎯 RollingUpdate মানে কী? ধরো ১০টা Pod আছে। নতুন version deploy করতে হবে। RollingUpdate এ একটা একটা করে পুরনো Pod বন্ধ করে নতুন চালু করা হয়। সব সময় কিছু Pod চালু থাকে — কোনো downtime নেই। পুরনো version থেকে নতুন version এ smooth transition।

📖 Output columns বিস্তারিত:

READY 1/1 = Pod এ 1টা container আছে, 1টাই ready (0/1 হলে container চালু হয়নি)
STATUS: Running = চলছে ✅ | Pending = অপেক্ষায় | CrashLoopBackOff = বারবার crash করছে ❌
RESTARTS: 5 মানে ৫বার crash করেছে — kubectl logs mypod --previous দিয়ে কারণ দেখো
AGE: 2m20s = 2 মিনিট 20 সেকেন্ড ধরে চলছে | 5d = 5 দিন

Services ও Ingress

❓ Service কেন দরকার?

Pods ephemeral — নতুন Pod তৈরি হলে নতুন IP পায়। তাহলে কোন IP তে request পাঠাবে? এজন্য দরকার Service — একটা stable virtual IP যেটা বদলায় না। Pod মরুক বা নতুন আসুক, Service IP একই থাকে। Service পেছনের Pods-কে request forward করে।

Service Labels এবং Selectors দিয়ে Pods identify করে। ReplicaSet তৈরির সময় network নিজে থেকে হয় না — Service আলাদা করে তৈরি করতে হয়।

Service types এবং request flow — Internet থেকে Pod পর্যন্ত

ClusterIP — Default Service Type

শুধু cluster এর ভেতরে accessible। Pod-to-Pod communication এর জন্য।

kubectl expose deploy nginx-deployment --port=80 --type=ClusterIP kubectl get svc # NAME TYPE CLUSTER-IP PORT(S) # nginx-deployment ClusterIP 10.43.139.215 80/TCP # Test করো cluster এর ভেতর থেকে kubectl run curl --image=curlimages/curl -i --tty -- sh curl 10.43.139.215

NodePort — বাইরে থেকে access

ClusterIP এর উপরে। Node এর একটা port (30000-32767) expose করে বাইরে।

apiVersion: v1 kind: Service metadata: name: my-nodeport-service spec: type: NodePort selector: app: nginx-deployment # এই label এর Pods select করবে ports: - protocol: TCP port: 80 # Service এর port (internal) targetPort: 80 # Pod এর port nodePort: 30000 # বাইরে থেকে এই port এ hit করো

Browser এ http://[Node-IP]:30000 দিলে nginx দেখবে!

LoadBalancer — Cloud এ External Access

NodePort এর উপরে। Cloud provider (AWS, GCP, Azure) এ automatically external load balancer তৈরি করে।

Default strategy: Round Robin — পালাক্রমে পাঠায়। যেমন ৩টা Pod: 1st request → Pod 1, 2nd → Pod 2, 3rd → Pod 3, 4th → আবার Pod 1। ক্রিকেটের batting order এর মতো! এটা static — কে বেশি busy সেটা দেখে না। Test environment এর জন্য ভালো।

Session persistence দরকার হলে Consistent Hash ব্যবহার করো — একই user সবসময় same Pod এ যাবে। Online shopping cart এ দরকার: না হলে প্রতি page reload এ login করতে হবে!

⚠️ নিজের server এ (on-premise) LoadBalancer ব্যবহার করতে MetalLB install করতে হয়।

Ingress — URL routing rules

Ingress হলো Service এর সামনে আরেকটা layer। URL দেখে কোথায় forward করবে সেটা ঠিক করে।

💾 Persistent Volumes — Data রাখো Pod ছাড়া

সমস্যা কী?

Pod মরে গেলে তার সব data হারিয়ে যায়। ধরো MySQL database Pod এ চালাচ্ছ — Pod crash করল, সব data গেল!

Persistent Volume (PV) Pod এর বাইরে থাকে। Pod মরলেও PV এবং তার data থাকে। পরের Pod সেই data-ই পাবে।

PV → PVC → StorageClass chain — Pod কীভাবে storage পায়
# PersistentVolume তৈরি (pv.yml) apiVersion: v1 kind: PersistentVolume metadata: name: datascientest-pv spec: capacity: storage: 10Gi # 10 গিগাবাইট storage দেবে accessModes: - ReadWriteOnce # একটা Node read-write করতে পারবে hostPath: path: /mnt/data # server এর কোন directory? storageClassName: slow # PVC এর সাথে match করানোর জন্য

📂 Access Modes — কে কীভাবে access করবে?

Access Modeমানে
ReadWriteOnce (RWO)একটা Node read ও write করতে পারবে
ReadWriteMany (RWX)অনেক Node read ও write করতে পারবে — shared storage
ReadOnlyMany (ROX)অনেক Node শুধু read করতে পারবে
ReadWriteOncePod (RWOP)শুধু একটা Pod পারবে — সবচেয়ে strict

🧪 Dummy/Test Dataset তৈরি করো — Download ব্যর্থ হলে ব্যবহার করো

Production এ বা offline এ কাজ করার সময় real dataset download নাও হতে পারে। এজন্য একটা synthetic (কৃত্রিম) dataset তৈরি করে রাখা ভালো।

🔐 Secrets — Password লুকিয়ে রাখো

কেন Secret? YAML এ সরাসরি লিখলে হয় না?

YAML file Git এ থাকে। সবাই দেখতে পায়। Password YAML এ লিখলে সেটা সবার কাছে expose হয়। Secret ব্যবহার করলে password base64 encode হয়ে store হয়।

base64 কী? এটা encryption না — শুধু encoding। "Hello" → "SGVsbG8=" হয়ে যায়। সহজে decode করা যায়। তাহলে কী লাভ? লাভ হলো YAML এ special characters (যেমন @, !, #) directly লিখলে parse error হয়। base64 সেটা safe করে। Real security আসে RBAC ও cluster access control থেকে।

# Password কে base64 এ convert করো echo -n 'Datascientest2023@!!!' | base64 # Output: RGF0YXNjaWVudGVzdDIwMjNAISE= # secret.yml apiVersion: v1 kind: Secret metadata: name: mariadb-rootpass type: Opaque data: password: RGF0YXNjaWVudGVzdDIwMjNAISE= # base64 encoded
kubectl apply -f secret.yml kubectl get secret kubectl describe secret mariadb-rootpass # Data section দেখাবে password কিন্তু value না, শুধু size # password: 20 bytes # Secret decode করো (check করতে) kubectl get secret mariadb-rootpass \ -o jsonpath='{.data.password}' | base64 --decode # Command দিয়ে Secret তৈরি kubectl create secret generic my-secret \ --from-literal=MYSQL_USER=admin \ --from-literal=MYSQL_PASSWORD=secret123

🏥 Health Checks — Pod সুস্থ আছে?

🫀 Liveness Probe

  • Pod চলছে কিনা check করে
  • Fail হলে Pod restart করে
  • TCP socket বা HTTP দিয়ে check
  • initialDelaySeconds: শুরু করার আগে কতক্ষণ wait

✅ Readiness Probe

  • Pod traffic নিতে ready কিনা check
  • Fail হলে Service থেকে remove করে
  • Ready হলে আবার Service এ add
  • App startup সময় নিলে important
livenessProbe: tcpSocket: port: 80 # TCP দিয়ে port 80 open কিনা check initialDelaySeconds: 5 # Pod চালু হওয়ার ৫ সেকেন্ড পরে শুরু করো periodSeconds: 5 # প্রতি ৫ সেকেন্ডে check করো failureThreshold: 3 # ৩ বার fail হলে restart করো readinessProbe: httpGet: path: / # HTTP GET / করে check port: 80 initialDelaySeconds: 5 periodSeconds: 3

Autoscaling — নিজে নিজে scale করো
HPA, VPA, Cluster Autoscaler — তিন ধরনের autoscaling
Autoscalerকী করে?কখন দরকার?
HPA
Horizontal Pod Autoscaler		 Pod এর সংখ্যা বাড়ায়/কমায়। CPU বা custom metrics দেখে। Traffic বেশি হলে আরও Pods চাই
VPA
Vertical Pod Autoscaler		 Pod এর CPU/Memory resource বাড়ায়/কমায়। Pod কে বড় করে। একটা Pod এর বেশি resource দরকার
CA
Cluster Autoscaler		 Cluster এ আরও Node যোগ করে বা সরায়। HPA করতে Node তে জায়গা নেই
HPA vs VPA — Horizontal (আরও Pods) vs Vertical (বড় Pod)

⛵ HELM কী?

ধরো তুমি Prometheus monitoring deploy করতে চাও। এতে লাগবে: Deployment, Service, ConfigMap, RBAC rules, PV/PVC — মোট ২০টা YAML file। সব আলাদাভাবে manage করা nightmare।

HELM হলো এই সব YAML কে একটা "package" (Chart) এ bundle করে। এক command এ install করো!

Ubuntu তে apt install nginx এর মতো Kubernetes এ helm install nginx bitnami/nginx।

📦 Helm 2 (পুরনো)

  • Client + Server architecture
  • Server = Tiller (cluster এ install)
  • Security সমস্যা ছিল
  • এখন deprecated

📦 Helm 3 (বর্তমান)

  • শুধু client — Tiller নেই!
  • সরাসরি kube-apiserver এর সাথে কথা বলে
  • বেশি secure ও simple
  • Library charts support করে

📊 Helm Chart কী? কেন দরকার?

Real use case — ৩টা Environment

ধরো তোমার ৩টা environment আছে: Dev, Staging, Production।

  • Dev: 1 replica, test database
  • Staging: 3 replicas, staging database
  • Production: 10 replicas, production database, HPA enabled

Helm ছাড়া: ৩ সেট আলাদা YAML file maintain করতে হবে। Helm দিয়ে: একটাই Chart, শুধু values file আলাদা!

# Chart structure my-app-chart/ ├── Chart.yaml # Chart এর metadata (নাম, version) ├── values.yaml # Default values ├── templates/ │ ├── deployment.yaml # {{ .Values.replicas }} দিয়ে template │ ├── service.yaml │ └── ingress.yaml └── charts/ # Dependency charts # Dev এ install করো helm install my-app ./my-app-chart -f dev-values.yaml # Production এ install করো helm install my-app ./my-app-chart -f prod-values.yaml # Upgrade করো helm upgrade my-app ./my-app-chart -f prod-values.yaml # Rollback করো helm rollback my-app 1

✅ Helm এর মূল সুবিধা: একটাই Chart, অনেক environment। DRY (Don't Repeat Yourself) principle মানো।
