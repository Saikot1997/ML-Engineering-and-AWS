💡 Capstone Lab থেকে মূল শিক্ষা

এই lab এ তুমি একটি real-world 3-tier architecture তৈরি করলে। Web tier (ALB + ASG), App tier (EC2 + EFS), Database tier (Aurora Multi-AZ)। প্রতিটি tier ই highly available — কোনো single point of failure নেই। Auto Scaling নিশ্চিত করে যে load বাড়লে নতুন servers আসে এবং কমলে চলে যায়।

🗺 DIAGRAM পড়ার গাইড — বাংলায়

এই diagram টি উপর থেকে নিচে পড়তে হয়। একদম উপরে বাম পাশে আছে Internet — সেটা VPC এর বাইরে। তারপর ধাপে ধাপে request ভেতরে ঢোকে তিনটা tier এ। ডান পাশে EFS এবং Auto Scaling এর info আছে।

STEP ①
🌐➡🚪
Internet → IGW
কোনো user browser এ WordPress URL type করলে request প্রথমে Internet এ যায়। সেখান থেকে AWS এর Internet Gateway (IGW) এ ঢোকে। IGW হলো VPC এর দরজা — বাইরের দুনিয়া থেকে ভেতরে ঢোকার একমাত্র রাস্তা।
STEP ②
⚖
ALB — Load Balancer
IGW থেকে request যায় Application Load Balancer (ALB) এ। ALB দুটো AZ এর Public Subnet এ span করে — diagram এ দেখো ALB box টা দুই AZ এর উপর দিয়ে যাচ্ছে। এটা দেখে কোন server কম busy, সেখানে request পাঠায়। Load সমানভাবে ভাগ হয়।
STEP ③
🔀
Public Subnet + NAT GW
Public Subnet এ আছে NAT Gateway। ⚠ এটা incoming traffic handle করে না! এটার কাজ উলটো — Private subnet এর server গুলো যখন software update করতে internet যেতে চায়, NAT সেই outbound request handle করে। Diagram এ হলুদ dashed arrow টা সেটাই দেখাচ্ছে।
STEP ④
🖥🖥
App Subnet — EC2 Servers
ALB request পাঠায় App Subnet এর EC2 servers এ — এগুলো private, সরাসরি internet থেকে access হয় না। এখানে WordPress run করছে। Auto Scaling Group (WP-ASG) এই servers manage করে — traffic বাড়লে নতুন server আসে (max 4), কমলে চলে যায়।
STEP ⑤
📁
EFS — Shared Storage
দুটো EC2 server একই Amazon EFS file system NFS দিয়ে mount করে — diagram এ teal dashed line। AZ-A তে কেউ image upload করলে AZ-B এর server ও সেটা দেখবে। WordPress এর files, themes, plugins সব এই shared storage এ।
STEP ⑥
🗂🗂
DB Subnet — Aurora
WordPress data (posts, users) থাকে Aurora তে। AZ-A তে Primary (Writer) — read+write। AZ-B তে Replica (Reader) — copy রাখে। Primary fail হলে Replica automatically Primary হয়। এটাই Multi-AZ failover।
❓ দুটো AZ কেন? — High Availability বোঝো
AZ = Availability Zone মানে আলাদা physical data center। প্রতিটা AZ এর আলাদা power, cooling, network। যদি AZ-A তে power cut হয় — AZ-B তে সব চলতে থাকবে। User কিছুই বুঝবে না।
এই lab এ প্রতিটা tier Multi-AZ:
• Public: PublicSubnet1 + PublicSubnet2
• App: AppSubnet1 + AppSubnet2
• DB: Aurora Primary + Replica
• EFS: দুই AZ তে mount target
• ALB: AWS managed HA
🔄 COMPLETE TRAFFIC FLOW — সম্পূর্ণ যাত্রা
User browser → 🚪 IGW → ⚖ ALB → 🖥 EC2 WordPress ↔ 📁 EFS + 🗂 Aurora DB
Outbound (software updates): EC2 → 🔀 NAT Gateway → 🚪 IGW → Internet
T1
Task 1: CloudFormation Template দিয়ে VPC তৈরি করো
Pre-configured YAML template upload করে সম্পূর্ণ network infrastructure deploy করো
STEP 1
In the AWS Management Console search box, search for and choose CloudFormation.
বাংলা
Console এর search box এ CloudFormation টাইপ করো এবং service টি open করো।
STEP 2
Choose Create stack → With new resources (standard). Select Choose an existing template → Amazon S3 URL. Paste the Task1TemplateUrl from the lab sidebar.
বাংলা
Create stack → With new resources চাপো। Template source: Amazon S3 URL select করো। Lab এর বাম পাশ থেকে Task1TemplateUrl copy করে paste করো। এটা automatically VPC, Subnets, IGW, NAT GW, Route Tables, Security Groups তৈরি করবে।
STEP 3
For Stack name, enter VPCStack. Leave all Parameters at default values. Click through Next → Next → Submit.
বাংলা
Stack name: VPCStack লিখো। Parameters সব default রাখো। Next → Next → Submit করো। Stack CREATE_IN_PROGRESS থেকে CREATE_COMPLETE হতে ~5 মিনিট লাগে।
STEP 4
After creation, check the Resources tab to see all created resources (VPC, Subnets, IGW, NAT GW, Route Tables). Check the Outputs tab for key-value pairs used in later tasks.
বাংলা
Resources tab এ দেখো কতগুলো resource তৈরি হয়েছে। Outputs tab এ important values থাকবে যা পরের tasks এ দরকার হবে। Events tab এ chronological order এ সব কার্যক্রম দেখতে পাবে।
💡Template টি locally save করতে Task1.yaml link এ right-click করো। ভবিষ্যতে নিজের AWS account এ use করতে পারবে।

Task 2: Amazon Aurora RDS Database তৈরি করো
Multi-AZ Aurora MySQL cluster তৈরি করো — DB Subnet Group সহ
STEP 1 — Subnet Group
Go to RDS console → Left nav: Subnet groups → Create DB subnet group. Name: AuroraSubnetGroup. VPC: LabVPC.
বাংলা
RDS console → Subnet groups → Create DB subnet group। Name: AuroraSubnetGroup। VPC: LabVPC select করো। DB Subnet Group বলে Aurora কোন subnets এ run করবে।
STEP 2 — Subnet Selection
Availability Zones: select zone ending in "a" and "b". Subnets: select CIDR 10.0.4.0/24 (AZ-a) and 10.0.5.0/24 (AZ-b). Choose Create.
বাংলা
AZ: "a" ending এবং "b" ending দুটো select করো। Subnets: 10.0.4.0/24 ও 10.0.5.0/24 — এগুলো Database subnets। Create করো।
STEP 3 — Aurora DB
Databases → Create database → Standard create. Engine: Aurora (MySQL Compatible). Template: Production. DB cluster identifier: MyDBCluster. Master username: admin.
বাংলা
Databases → Create database। Engine: Aurora (MySQL Compatible)। Template: Production। Cluster ID: MyDBCluster। Username: admin। Password: Lab এর LabPassword use করো।
STEP 4 — Instance Config
DB instance class: Burstable classes → db.t3.medium. Multi-AZ: Create an Aurora Replica in different AZ. VPC: LabVPC. DB subnet group: aurorasubnetgroup. Security Group: RDSSecurityGroup. Uncheck: Encryption, Enhanced monitoring, Auto minor upgrade, Deletion protection.
বাংলা
Instance type: db.t3.medium (Burstable)। Multi-AZ: Aurora Replica তৈরি করো — High Availability এর জন্য। Public access: No। Security Group: RDSSecurityGroup। Initial database name: WPDatabase। Encryption, Enhanced monitoring, Auto minor upgrade, Deletion protection সব OFF করো।
STEP 5 — Save Metadata
After creation, note the Writer endpoint (Connectivity & security tab), Master username, DB name — you'll need these in Task 5.
বাংলা
DB তৈরি হলে Writer endpoint copy করো (Connectivity tab)। এটা Task 5 এ CloudFormation parameters এ দরকার। Username (admin), Password (LabPassword), DB name (WPDatabase) মনে রাখো।
⚠️"Failed to turn on enhanced monitoring" error দেখলে ignore করো — এটা expected। Lab environment এ permissions limited।

Task 3: Amazon EFS File System তৈরি করো
Shared storage layer — app servers NFS দিয়ে একই filesystem share করবে
STEP 1
Search for and open EFS console → Create file system → Customize. Name: myWPEFS. Availability: Regional. Performance: General Purpose. Throughput: Bursting. Uncheck: Automatic backups, Encryption at rest.
বাংলা
EFS console → Create file system → Customize। Name: myWPEFS। Availability: Regional (দুই AZ তে available)। Performance: General Purpose। Throughput: Bursting। Automatic backups ও Encryption — দুটোই OFF করো।
STEP 2 — Network / Mount Targets
VPC: LabVPC. Add two mount targets: AZ ending "a" → AppSubnet1, AZ ending "b" → AppSubnet2. Security group: remove default, select EFSMountTargetSecurityGroup for both.
বাংলা
VPC: LabVPC। Mount targets: AZ "a" এ AppSubnet1, AZ "b" এ AppSubnet2। Security group: Default সরিয়ে দিয়ে EFSMountTargetSecurityGroup দাও। File system policy page: Next (skip)। Create।
STEP 3 — Copy File System ID
After creation, go to File systems in left nav. Copy the File system ID (format: fs-xxxxxxxx). You'll need this in Task 5.
বাংলা
EFS তৈরি হলে left nav → File systems। File system ID copy করো (যেমন: fs-a1234567)। Task 5 এ CloudFormation এ WPElasticFileSystemID parameter এ paste করতে হবে।
📌Tag key: Name, Tag value: myWPEFS — এটাও configure করো Additional settings থেকে।

Task 6: Auto Scaling Group তৈরি করো
WordPress application servers deploy করো এবং scaling policy configure করো
STEP 1
EC2 → Auto Scaling → Auto Scaling Groups → Create Auto Scaling group. Name: WP-ASG. Launch template: select the template created in Task 5.
বাংলা
EC2 → Auto Scaling Groups → Create Auto Scaling group। Name: WP-ASG। Launch template: Task 5 এ তৈরি template select করো।
STEP 2 — Network
VPC: LabVPC. Availability Zones and subnets: select AppSubnet1 and AppSubnet2.
বাংলা
VPC: LabVPC। Subnets: AppSubnet1 ও AppSubnet2 — দুই AZ তে app servers থাকবে।
STEP 3 — Load Balancer Integration
Attach to an existing load balancer → Choose from your load balancer target groups → select myWPTargetGroup | HTTP. Turn on: Elastic Load Balancing health checks. Health check grace period: 300 seconds (or default).
বাংলা
Existing load balancer attach করো। Target group: myWPTargetGroup | HTTP। ELB health checks turn on করো। Health check grace period: 300 seconds। এটা instance launch এর পর WordPress setup হওয়ার সময় দেয়।
STEP 4 — Group Size
Desired capacity: 2. Minimum capacity: 2. Maximum capacity: 4. Scaling policy: Target tracking scaling policy (defaults). Enable group metrics collection in CloudWatch.
বাংলা
Desired: 2, Min: 2, Max: 4। Scaling: Target tracking scaling policy (default values রাখো)। CloudWatch monitoring: Enable group metrics collection চেক করো।
STEP 5 — Tags & Create
Add tag: Key = Name, Value = WP-App. Review and Create Auto Scaling group.
বাংলা
Tag: Key = Name, Value = WP-App। Create করো। ASG স্বয়ংক্রিয়ভাবে 2টি EC2 instance launch করবে। Activity tab এ progress দেখো।
STEP 6 — Verify & Test
Verify: EC2 → Target Groups → myWPTargetGroup → Targets tab → wait for Health Status to show "healthy". Then: copy the ALB DNS name and append /wp-login.php → open in browser. Login: username wpadmin, password: LabPassword.
বাংলা
Target Groups → myWPTargetGroup → Targets tab → Health status: healthy হওয়া পর্যন্ত wait করো (~5 min)। তারপর browser এ ALB DNS name + /wp-login.php open করো। Login: wpadmin / LabPassword → WordPress dashboard দেখবে!
